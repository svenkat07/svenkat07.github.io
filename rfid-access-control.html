What I’m exploring

An RFID access workflow with explicit decisions: granted, denied, duplicate, busy or invalid. The reconstructed C++ controller is shared by the host simulator and an ESP32 firmware draft.

The system

The firmware draft reads an MFRC522 over SPI, checks invented demo UIDs and requests a three-second relay pulse. JSON events are emitted over USB serial. A host-side Python adapter writes a local mock, or can optionally send a captured file to Firebase over HTTPS.

Design decisions

Repeated consecutive scans within two seconds are suppressed. Scans while the relay is active cannot extend its pulse. The host adapter records grants only, and uses deterministic event keys for repeatable PUT retries within a session.

What is tested

Native C++ tests cover approval, rejection, malformed inputs, duplicate handling, busy state, relay expiry and timer wrap. Three Python tests cover filtering, deduplication and session validation. The seven-event simulation produces three mock grant records.

The boundary of the prototype

This reconstruction uses a host-side cloud adapter, not direct ESP32 Wi-Fi uploads. Embedded compilation, physical RFID reads, relay behaviour and live Firebase writes remain unvalidated. A grant is not proof of entry or actual attendance. UID matching is cloneable and unsuitable as real building access security.

Next on the bench

Compile the ESP32 firmware, validate wiring and timing on real hardware, then collect and document new measurements. Simulation results remain clearly separated from physical validation.
