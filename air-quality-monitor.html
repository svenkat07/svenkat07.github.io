What I’m exploring

How sensor readings become meaningful application states: startup, normal, alert and sensor fault. This reconstruction shares C++ monitoring logic between a host simulator and an ESP32 firmware draft.

The system

The firmware draft separates a two-second sensor task from the networking task with a one-element FreeRTOS mailbox. MQTT reconnection therefore does not own the sensor-sampling loop. The local indicator responds to alert and fault states.

Design decisions

Exponential smoothing reduces analogue jitter. Hysteresis avoids rapid alert switching near thresholds. Invalid DHT readings are encoded as JSON null. Stale samples are discarded after ten seconds; this is latest-state telemetry, not a lossless event recorder.

What is tested

Native C++ tests cover startup, temperature and analogue alerts, hysteresis, recovery, invalid values and timer wrap. The host simulator produces 120 explicitly synthetic records and a static report. The firmware has not been compiled or tested on hardware.

What the numbers mean

MQ-135 readings are divided ADC-node millivolts, not calibrated CO₂, ppm or AQI. The 60-second application startup gate is not sensor conditioning or calibration. DHT22 uses its timed digital protocol; MQ-135 uses ADC. Neither is an I²C/SPI peripheral in this implementation.

Next on the bench

Compile the ESP32 firmware, validate wiring and timing on real hardware, then collect and document new measurements. Simulation results remain clearly separated from physical validation.
